# リサーチファースト（Research Before Code）

## 原則: 1回のリリースで正しく動く状態にする

API移行や新サービス導入で、推測→実装→エラー→修正→再リリースのサイクルを回すのは禁止。
事前に仕様を確認し、1回で正しく実装する。

## 必須リサーチ項目

新しいAPI・モデル・SDKを使う前に、以下を公式ドキュメントで確認:

| 項目                 | 確認方法                                      |
| -------------------- | --------------------------------------------- |
| リクエスト構造       | API referenceのサンプルリクエストを読む       |
| フィールド名・ネスト | v1→v2等でのフィールド変更がないか確認         |
| 対応リージョン       | モデル/サービスのリージョン可用性ページを確認 |
| 機能制限             | 組み合わせ不可の機能、同時使用制限を確認      |
| 認証方式             | APIキー/OAuth/サービスアカウントの違いを確認  |
| レート制限           | クォータ・制限値を確認                        |

## 確認の証跡

リサーチ結果は実装開始前にユーザーに共有するか、コード内コメントとして残す。
「ドキュメントを読んだ」という記憶ではなく、具体的な仕様値（リージョン名、フィールド名等）を示せること。

## 実例（このプロジェクトで発生した事故）

chirp_2→chirp_3移行で3回のリリースを浪費:

1. `phrases` → `inlinePhraseSet` ラップが必要（API構造変更）
2. `us-central1` にchirp_3が存在しない（リージョン可用性）
3. diarization + adaptation の同時使用不可（機能制限）

3つとも事前のドキュメント確認で判明する情報だった。
