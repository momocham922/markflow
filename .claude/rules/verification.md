# 検証ルール（Verification Rules）

## 原則: 自分の出力を信用するな、システム状態を確認しろ

「コマンドを実行した」と「変更が反映されている」は別の事実。
完了報告の前に、変更先のシステムで実際の状態を確認する。

## Cloud Run デプロイ後の必須検証

デプロイコマンド実行後、以下の2つを**両方**実行するまで「デプロイ完了」と報告してはならない。

1. **リビジョン確認**: `gcloud run services describe <service> --project <project> --region <region> --format="value(status.traffic[0].revisionName)"` で新しいリビジョンがトラフィック100%であることを確認
2. **ライブ動作確認**: デプロイした変更に関連するエンドポイントに実際にリクエストを送り、期待する挙動を確認

## API/モデル移行の必須検証

新しいAPI・モデル・サービスに切り替える場合:

1. **実装前**: 公式ドキュメントで以下を確認してから実装開始
   - リクエスト/レスポンス構造（フィールド名、ネスト構造）
   - 対応リージョン・エンドポイント
   - 機能の組み合わせ制限（同時使用不可の機能等）
   - 必須パラメータの変更
2. **実装後**: curl等でAPIを直接叩いて動作確認してからデプロイ
3. **デプロイ後**: 上記「Cloud Runデプロイ後の必須検証」を実行

## 完了報告の条件

以下をすべて満たすまで完了報告禁止:

- コード変更 → ビルド成功 → テスト通過
- バックエンド変更 → デプロイ済み + リビジョン確認 + ライブ動作確認
- フロントエンド変更 → リリーススクリプト実行済み + GitHub releaseのURL確認
- ユーザーが体感する変化 → 何が変わるか具体的に説明できる

## 禁止事項

- コマンド出力に「deployed」と書いてあったから完了、という判断
- 前セッションの報告を検証せずに引き継ぐこと
- 「検証した」と記憶しているが証跡（コマンド出力）がない状態での完了報告
